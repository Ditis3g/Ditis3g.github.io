로봇의 센서는 현실을 그대로 복사하지 않는다. 카메라는 픽셀을, LiDAR는 거리 샘플을, 관절 센서는 각도와 속도를, 힘 센서는 접촉 변화를 보낸다. 피지컬 AI가 필요한 것은 이 숫자의 나열이 아니라 “지금 컵이 어디에 있고, 손은 어떤 자세이며, 다음 행동을 해도 되는가”라는 작업 상태다.

## 관측과 상태는 다르다

관측은 센서가 방금 측정한 값이고, 상태는 여러 관측과 과거 행동을 종합한 현재의 설명이다. 카메라 한 프레임에는 손가락이 컵에 닿은 것처럼 보여도, 직전 프레임에서 컵이 미끄러졌다는 사실은 빠져 있을 수 있다. 상태 추정은 이런 시간의 문맥을 보충한다.

| 원시 관측 | 작업에 필요한 상태 |
| --- | --- |
| 영상 속 윤곽 | 컵의 위치·자세·가림 정도 |
| 관절 각도 | 손끝의 실제 위치와 도달 여유 |
| 힘 변화 | 접촉·파지·미끄러짐 여부 |
| 여러 시점의 변화 | 물체가 움직이는 방향과 속도 |

센서 융합은 센서를 많이 붙이는 일이 아니다. 서로 다른 센서가 어느 시간과 좌표계에서 같은 사건을 설명하는지 맞추는 일이다. 카메라가 물체를 보았지만 관절 상태가 오래된 값이면 정책은 현재가 아닌 과거의 몸을 기준으로 행동한다.

## 상태가 불확실할 때의 행동

상태 추정에는 항상 오차가 있다. 중요한 것은 오차를 없애는 것이 아니라, 오차가 커졌을 때 행동을 바꾸는 것이다. 물체 위치가 확실하면 접근하고, 위치가 흔들리면 속도를 낮추고, 가림이 심하면 시점을 바꾸며, 센서가 서로 모순되면 실행을 보류한다.

```text
센서 관측 → 시간·좌표 정렬 → 상태 추정 → 신뢰 범위 확인
                                      ↓
                           접근·재관찰·대기·중단
```

이 구조는 인식과 판단을 다시 연결한다. “무엇인지 모른다”는 출력도 시스템에 유용한 정보다. 불확실성을 숨기지 않고 행동의 속도와 범위에 반영할 때 센서의 한계가 안전한 운영 규칙으로 바뀐다.

## 설계자가 남겨야 할 기록

상태 추정기를 개선하려면 원시 센서, 보정 정보, 추정 상태, 신뢰도, 정책이 받은 입력을 함께 기록해야 한다. 최종 판단만 저장하면 오류가 센서에서 시작했는지 융합 과정에서 생겼는지 알 수 없다. 3부의 행동 데이터도 이 상태 기록 위에서만 의미를 가진다.

## 함께 읽는 보충 내용 — 작업을 상태와 전환으로 설계하기

언어로 “컵을 가져와”라고 말하면 사람은 준비·접근·파지·운반·놓기를 자연스럽게 나눈다. 로봇 시스템도 작업을 상태와 전환으로 표현하면 목표와 몸의 움직임 사이를 연결하기 쉬워진다. 이는 모든 행동을 딱딱한 규칙으로 고정하자는 뜻이 아니라, 현재 어디에 있고 다음에 무엇을 확인해야 하는지를 명확히 하자는 뜻이다.

### 컵 가져오기 상태 지도

```text
준비 → 대상 확인 → 접근 → 정렬 → 접촉·파지
  ↑       │          │       │          │
  └ 재관찰┴──────────┴───────┴── 실패 복구
                                      ↓
                              운반 → 놓기 → 성공 확인
```

각 상태에는 진입 조건과 종료 조건이 있다. 접근 상태는 컵이 보이고 도달 가능할 때 시작하며, 손끝이 지정 범위에 들어오거나 시야가 가려지면 다음 상태로 넘어가거나 복구한다. 성공 확인은 그리퍼가 닫혔다는 신호가 아니라 컵이 실제 목표 위치에 남았는지를 본다.

### 학습과 규칙의 경계

상태의 이름과 안전 전환은 명시적으로 두는 편이 설명하기 쉽다. 하지만 “어느 모서리를 먼저 잡을지”, “가려진 컵이 어느 위치일지”, “접촉 힘을 얼마나 조절할지”는 데이터 기반 정책이 더 유연하게 처리할 수 있다.

| 명시적으로 고정하기 좋은 것 | 학습으로 맡기기 좋은 것 |
| --- | --- |
| 비상 정지·작업 영역·최대 힘 | 물체 선택·접근 방향 |
| 성공·실패 판정의 큰 기준 | 미세한 속도·힘·자세 |
| 상태 전환의 금지 조건 | 예외 상황의 복구 후보 |

이 경계가 있으면 모델이 불확실해도 시스템 전체가 무너지지 않는다. 정책은 상태 안에서 행동을 제안하고, 상태 관리자는 결과를 확인하며, 안전층은 어떤 상태에서도 넘지 말아야 할 경계를 지킨다.

### 상태 설계는 평가 설계이기도 하다

작업을 상태로 나누면 성공률을 단계별로 볼 수 있다. 접근에서 많이 실패한다면 시야와 경로를, 접촉에서 실패한다면 그리퍼와 힘을, 놓기에서 실패한다면 성공 판정과 목표 위치를 점검할 수 있다. 이 구조는 5부의 시뮬레이션 평가에도 그대로 사용된다.
